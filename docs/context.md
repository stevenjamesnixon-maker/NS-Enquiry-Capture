## 0. Read this first

1. **The Email Capture plug-in may be SuiteScript 1.0 only.** The 22 Sep brief specifies a
   SuiteScript 2.1 implementation (`@NScriptType plugintypeimpl`, `N/record`, AMD `./lib/`
   modules). Oracle's current help for the Email Capture plug-in states *"Only SuiteScript 1.0
   is supported for use with the Email Capture Plug-in"*, and documents the entry point as
   `process(email)`. If that holds, the brief's module structure cannot be built as written.
   See §6. Nothing is to be implemented until Steve decides the way forward.

2. **This repo never touches the Opportunity.** The Opportunity is raised by
   `customscript_project_ue` in its `afterSubmit` when a Project is created with
   `custrecord_proj_create_qr_pq` ticked. That script is owned by another project; a read-only
   copy is in `reference/`. Do not create, edit or delete Opportunities from here, and do not
   edit `reference/project_ue.js`.

3. **No numeric internal IDs in the repo.** Statuses, categories, currency, forms, folders,
   employees and web categories all come in through script parameters. Script IDs
   (`custscript_*`, `custentity_*`, `customrecord_*`) may be committed. The inbound capture
   address is account-specific and **must not be committed** either.

4. **A shared-mailbox rule must *forward*, not *redirect*.** A redirect keeps the prospect's
   address as the From, the prospect is not a trusted sender, and the message is dropped
   without notification. That drop is deliberate: anything else turns the capture address into
   a spam relay.

5. **List and select values come back raw.** `search.lookupFields` returns `[]` for an empty
   select, never `[{ value: '' }]`. Never read `[0].value` unguarded. The raw value the
   Customer search returns for `stage` has not been confirmed; log it before relying on it.

## 1. What this solves

Enquiries arrive in personal inboxes and on the website. They are re-keyed by hand, or not at
all. The account already has the second half of the pipeline: save a Project with *Auto Create
QRs and Prequotes* ticked and the Opportunity appears. The missing first half is an inbound
address that turns an email into an entity and a Project, and tells someone what it did.

Three sources will send to the capture address, and all three must work from day one:

| Source | Sender seen by the plug-in | Enquirer found from |
|---|---|---|
| A sales rep forwarding from Outlook | the rep (an employee) | the forwarded header block |
| The shared mailbox, via a **forward** rule | the shared mailbox (trusted sender) | the forwarded header block |
| The website's Gravity Forms plugin | the website sender (trusted sender) | labelled fields in the body |

## 4. Architecture

```
email ──► capture address ──► plug-in
                                 │ 1 classify sender: employee / trusted / untrusted (drop)
                                 │ 2 identify the enquirer from the body
                                 │ 3 find the entity by exact email, or create a Lead
                                 │ 4 createProjectForEntity(): duplicate check, Project save
                                 │      with custrecord_proj_create_qr_pq ticked, files saved and
                                 │      attached ──► customscript_project_ue afterSubmit
                                 │                     raises the Opportunity, writes it to
                                 │                     custrecord_proj_lead_opp
                                 │ 5 Message on the entity and the Opportunity
                                 │ 6 outcome email to the shared mailbox (cc the forwarding rep)
```

Confirmed facts this design rests on:

- **Project record** `customrecord_project` is auto-numbered `PR#####` with Include Name, so
  `name` is the number and `altname` the title. Field-level mandatory:
  `custrecord_proj_customer` (Select → Customer, parent) and `custrecord_proj_address` (Text
  Area). The form adds `custrecord_proj_build_type`. `custrecord_proj_sales_rep` sources from
  the customer's sales rep; `custrecord_proj_cust_stage` sources from the customer's stage.
- **`record.Type.LEAD`** creates a Customer record at Lead stage. Lead and Prospect stages are
  both in use.
- **Customer form NH Customer Form (V1)** makes these mandatory: `entityid` (auto), `category`,
  `entitystatus`, `currency`, `custentitycust_sys_dep`, and two **hidden** mandatory fields,
  `custentity_cust_vat_rate` and `custentity_web_category`. A scripted Lead must supply all
  six values. The types of `custentitycust_sys_dep` and `custentity_cust_vat_rate` are **not
  yet recorded**.
- **Opportunity form NH Opportunity 2026** carries the client script `Opportunity.js`. It does
  not run on scripted creates, and nothing here depends on it.
- **Native Duplicate Detection** on Customer matches on email domain only. It is a UI warning,
  not a rule a script can use. This project matches on the exact address only.
- **Employee `email`** is the source of truth for who a person is.

## 5. Standing warnings and deliberate decisions

These will look wrong to a fresh reader. Do not reverse them.

- **The plug-in never touches the Opportunity.** If the Opportunity is missing after the
  Project save, the outcome email says so and a person reads the `customdeploy_project_ue`
  execution log, which must be at **Audit**, not Error.
- **Exact email match only.** No domain match, no company-name match. Other entities sharing
  the exact address are reported, never merged.
- **Several exact matches attach to the highest stage, newest first,** and the rest are
  reported.
- **Project saved with `ignoreMandatoryFields: true`; Lead saved without it.** The Project's
  blanks are for the rep to fill; a Lead's blanks are things the script should have known.
- **Every Lead is a Company,** named from the display name.
- **Existing entities keep their sales rep.** Only a new Lead gets one: the forwarding
  employee, or the *- Reassign Using Territories -* value for generic sources.
- **Untrusted senders are dropped without notification.** Audit log only.
- **Forward, not redirect,** for shared-mailbox rules (§0.4).
- **The outcome email goes to the shared mailbox, cc the forwarding rep,** and carries no
  `relatedRecords`, so it never lands on the entity's Communication tab.
- **No rollback on partial failure.** A created Lead stays; the outcome email says exactly
  what exists.
- **Attachments are saved before they are attached, with prefixed names,** because
  `mediaitem` needs File Cabinet IDs and the File Cabinet overwrites by name.

### Notes on `reference/project_ue.js` (owned elsewhere; never modified here)

- It is `@NApiVersion 2.x`, not 2.1, and hardcodes internal IDs for the quote types, the Sales
  department and the New / Existing / Returning values. That is the owning project's business;
  this repo copies none of those values.
- `nerCalc()` looks up `lastsaledate` with `record.Type.CUSTOMER`. A Lead has no last sale, and
  any lookup failure is caught, so a new Lead resolves to New either way. No change needed.
- The Opportunity is saved with `ignoreMandatoryFields: true`, and no `salesrep` is set, so it
  sources from the entity. `redirect` is guarded to the UI context, so a scripted Project save
  is not redirected.
- The lead-Opportunity write-back uses `record.submitFields`, which re-runs the UE as an
  `edit`. That pass is harmless (nothing it compares has changed).
- `getSalesRep()` is defined and never called, and the comment on `opportunityCustomers()`
  says "used only by the oldRecord fallback" when it is called on every reconcile. Both are
  cosmetic. Report them to the owning project if convenient.
- **To confirm in the account:** the Execution Context filter on `customdeploy_project_ue` must
  include the context the plug-in runs in. Otherwise a Project saved by the plug-in raises no
  Opportunity, and nothing errors.

## 6. Known issues and limitations

- **Blocking: SuiteScript version of the plug-in.** See §0.1. The 22 Sep brief's items to verify
  also included the entry-point signature, the Email object's accessors and whether the
  Plug-in Implementation record takes script parameters. From Oracle's help as far as it could
  be reached (the help site itself was blocked from the implementation environment; the
  statements below come from Oracle's page text as indexed by search):
  - Only SuiteScript 1.0 is supported for Email Capture plug-in implementations.
  - The entry point is `process(email)`. The Email object offers `getFrom()`, `getTo()`,
    `getCc()`, `getReplyTo()`, `getSentDate()`, `getSubject()`, `getTextBody()`,
    `getHtmlBody()` and `getAttachments()`.
  - The address object returned by `getFrom()` offers `getName()` and **`getEmail()`**, not
    `getAddress()` as the brief has it.
  - The implementation has an **Execute As Role** field. It **cannot be Administrator**; Oracle
    recommends a custom role with the SuiteScript permission. The Lead, Project, file, attach
    and Message permissions must be granted to that role.
  - Whether the implementation record has a Parameters subtab was **not** confirmed.
- **Gravity Forms' default notification body** (`{all_fields}`) is an HTML table with the label
  and the value in **separate rows**, not `Label: value` on one line. The labelled-field parser
  in the brief expects one line. Either the notification is configured with `Label: value`
  lines, or the parser changes. Undecided.
- **Replies to the "unidentified" email** go to the notify-author employee, not to the capture
  address, unless that email sets a reply-to. The capture address is not currently known to the
  plug-in (it is not a parameter and must not be committed). Undecided.

## 8. Deployment sequence

Nothing to deploy yet. The planned sequence, once the blocker in §6 is settled:

1. Steve creates `SuiteScripts/Nuheat/Enquiry Capture/` and `lib/` inside it, plus the
   attachments folder.
2. Upload `lib/` first, in this order: config, parse, project, records, notify. Then the
   plug-in.
3. Customization › Plug-ins › Plug-in Implementations › New, type **Email Capture**. Set the
   log level to **Audit** and the Execute As Role (not Administrator). Record the generated
   inbound address in the account; **do not commit it.**
4. Set the parameters.
5. Raise `customdeploy_project_ue`'s log level from Error to **Audit**, and confirm its
   Execution Context filter includes the plug-in's context.
6. Configure the shared-mailbox rule as **forward**, not redirect.
7. Confirm every rep's employee record carries the email address they forward from.
